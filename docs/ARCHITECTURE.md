## Почему нужен сервер

Studio не может обратиться к другой Studio: нет ни адреса, ни постоянного соединения.
Плюс главное — **вы редко работаете одновременно**. Нужен кто-то всегда включённый,
кто примет изменения и подержит, пока второй не появится.

Пробовали три посредника:

| Посредник | Почему не подошёл |
|---|---|
| DataStore Roblox | Привязан к одному месту. У вас разные места |
| Open Cloud | Roblox запрещает отправлять ключи на свои адреса из Luau |
| **Свой сервер** | Работает. Домен и сертификат не нужны |

## Модули плагина

### Config
Все пределы, списки переносимых классов и свойств. Единственное место, куда стоит
заглядывать для настройки.

### Serialize
Свойства Roblox в JSON и обратно. Поддерживает `Vector3`, `CFrame`, `Color3`, `UDim`,
`UDim2`, `Vector2`, `NumberRange`, `BrickColor`, `PhysicalProperties`, перечисления
и ссылки на другие объекты.

Значения кодируются с явным полем-меткой:

```lua
CFrame.new(1, 2, 3)  →  { __t = "cf", d = {1, 2, 3, 1,0,0, 0,1,0, 0,0,1} }
```

Метка нужна, чтобы на другой стороне знать, во что превращать числа. Поле `d` обязательно:
таблица со строковым ключом и числовыми индексами одновременно **не выживает в JSON** —
числовые ключи становятся строковыми.

### Tree
Обход проекта и сравнение снимков.

Снимок — это карта `идентификатор → запись`. Идентификатор хранится скрытым атрибутом
`__vsid` прямо на объекте и **едет вместе с ним**. Поэтому:

- переименование объекта — это изменение, а не «удалили одно, создали другое»;
- перетаскивание в другую папку — тоже изменение;
- копия объекта (`Ctrl+D`) получает новый идентификатор, потому что обход замечает повтор.

У каждой записи есть отпечаток — дешёвый хэш свойств. Сравнение снимков сводится
к сравнению отпечатков.

Не переносятся: персонажи (всё, внутри чего есть `Humanoid`), служебные объекты с именами
на `__`, классы вне списка.

### Apply
Применение чужих изменений. Порядок важен:

1. **Создание** — несколько проходов, потому что родитель может приехать в том же пакете
   и ещё не существовать.
2. **Изменение** — с проверкой конфликтов.
3. **Ссылки** — отдельным проходом, когда все цели уже созданы. Иначе сварка искала бы
   деталь, которой ещё нет.
4. **Удаление** — от самых глубоких к корню, иначе родителя снесём раньше детей.

Меши — особый случай. Свойство `MeshId` **запрещено записывать**:

```
The current thread cannot write 'MeshId' (lacking capability NotAccessible)
```

Поэтому меш собирается через `AssetService:CreateMeshPartAsync`, а точность отрисовки
и столкновений задаётся **при создании** — присвоить их потом нельзя. Собранные меши
кешируются: первый стоит запроса к Roblox, остальные копируются за 0,1 мс.

### Net
Единственное место, знающее про HTTP. Ключ доступа уходит заголовком `x-russteam-key`.

Roblox запрещает такие заголовки при обращении к **своим** адресам, но на чужие домены
пропускает — это и делает схему возможной.

### Panel
Панель. Ничего не решает: получает состояние и сообщает о нажатиях наружу.

## Обмен

Один запрос делает всё сразу — втрое меньше обращений, чем при раздельных.

```
POST /v1/sync
{
  "channel": "TEAM-4821",
  "me": "707163568",
  "name": "vlad",
  "since": { "3845084819": 17 },     ← до чего я дочитал чужие ленты
  "events": [ ... ]                   ← моя разница, необязательно
}
```

```
200 OK
{
  "n": 42,                            ← номер моей пачки
  "batches": [ ... ],                 ← чужое, чего я не видел
  "roster": { ... },                  ← кто в канале
  "more": false,                      ← остались ли ещё пачки
  "dropped": 0                        ← сколько непрочитанного пришлось выбросить
}
```

## Хранение на сервере

Один файл на канал, внутри две части:

**Ленты** — по одной на участника. Каждый пишет только в свою, поэтому одновременная
работа не приводит к столкновениям.

**Перекличка** — кто когда отмечался, сколько у него неотправленного, до чего он дочитал
чужие ленты.

Пачка живёт, **пока её не забрали все живые участники**. Забрали — остаётся запас
в 20 последних. Молчащий больше недели выпадает из переклички и перестаёт держать чистку.

Данные держатся в памяти, на диск сбрасываются раз в секунду отдельным потоком: иначе
файл перечитывался бы на каждый запрос.

## Конфликты

С каждым изменением едет отпечаток той версии, от которой человек отталкивался.
Получатель сравнивает три вещи: свою текущую версию, свою точку отсчёта и присланный
отпечаток.

Если правил и он, и я, от общей точки — изменение **не применяется**, а попадает в список
с выбором. Автоматического слияния двух версий скрипта нет: это отдельная большая работа.

## Пределы и почему они такие

| Предел | Значение | Откуда |
|---|---|---|
| Порция отправки | 8000 изменений | Замер: 20 000 (3,5 МБ) уходят за 0,66 с, 60 000 (10,6 МБ) Roblox обрывает по таймауту |
| Запрос | 32 МБ | Больше Studio всё равно не отправит |
| Ответ приёма | 4 МБ | Остаток догружается следующим заходом |
| Лента участника | 512 МБ | ≈ 3 млн изменений, дальше предохранитель |
| Обход | 8000 объектов | Защита от гигантских мест; при обрыве плагин предупреждает |
| Частота | 300 запросов/мин с адреса | Защита от заваливания |
| Большая пачка | 400 изменений | Больше — нужно подтверждение человека |

## Известные ограничения

**Union и Negate.** Форма после объединения хранится на серверах Roblox. Разобрать готовый
юнион на исходные детали из кода невозможно — метода `SeparateAsync` не существует.
`GeometryService:UnionAsync` умеет собирать новый, но исходных деталей у нас нет.

**Terrain.** Воксели весят десятки мегабайт и в обмен не помещаются.

**Приватные ассеты.** Едет ссылка `rbxassetid://...`, а не файл. Если ассет не расшарен,
у напарника будет пусто.

**Слияние скриптов.** Две версии одного файла не сливаются: человек выбирает одну.
